ဤလမ်းညွှန်သည် Llámenos ဖြန့်ကျက်မှုပုံစံများနှင့် ပလက်ဖောင်းအားလုံးရှိ အဖြစ်များသော ပြဿနာများနှင့် ၎င်းတို့၏အဖြေများကို ဖော်ပြသည်။

## Docker ဖြန့်ကျက်မှုပြဿနာများ

### Container များစတင်ရန်ပျက်ကွက်ခြင်း

**ပျောက်ဆုံးနေသော ပတ်ဝန်းကျင် variable များ-**

Docker Compose သည် ပရိုဖိုင်လုပ်ထားသည့်အရာများအပါအဝင် ဝန်ဆောင်မှုအားလုံးကို စတင်ချိန်တွင် အတည်ပြုသည်။ ပျောက်ဆုံးနေသော variable များအကြောင်း အမှားများတွေ့ပါက သင်၏ `.env` ဖိုင်တွင် လိုအပ်သော တန်ဖိုးအားလုံးပါဝင်ကြောင်း သေချာပါစေ-

```bash
# Docker Compose အတွက် .env တွင် လိုအပ်သည်
PG_PASSWORD=your_postgres_password
STORAGE_ACCESS_KEY=your_rustfs_access_key
STORAGE_SECRET_KEY=your_rustfs_secret_key
HMAC_SECRET=your_hmac_secret
ARI_PASSWORD=your_ari_password       # Asterisk မသုံးလျှင်တောင်လိုအပ်
BRIDGE_SECRET=your_bridge_secret     # Asterisk မသုံးလျှင်တောင်လိုအပ်
ADMIN_PUBKEY=your_admin_hex_pubkey
```

Asterisk bridge ကိုမသုံးလျှင်တောင် Docker Compose သည် ၎င်း၏ဝန်ဆောင်မှုသတ်မှတ်ချက်ကို အတည်ပြုပြီး `ARI_PASSWORD` နှင့် `BRIDGE_SECRET` ကိုသတ်မှတ်ထားရန် လိုအပ်သည်။

**Port ပဋိပက္ခများ-**

Port တစ်ခုကိုအသုံးပြုပြီးသားဖြစ်ပါက မည်သည့်လုပ်ငန်းစဉ်ကကိုင်ထားသည်ကိုစစ်ဆေးပါ-

```bash
# Port 8787 (Worker) ကိုအသုံးပြုနေသည်ကိုစစ်ဆေးရန်
sudo lsof -i :8787

# Port 5432 (PostgreSQL) ကိုအသုံးပြုနေသည်ကိုစစ်ဆေးရန်
sudo lsof -i :5432

# Port 9000 (RustFS) ကိုအသုံးပြုနေသည်ကိုစစ်ဆေးရန်
sudo lsof -i :9000
```

ပဋိပက္ခဖြစ်နေသော လုပ်ငန်းစဉ်ကိုရပ်တန့်ပါ သို့မဟုတ် `docker-compose.yml` တွင် port mapping ကိုပြောင်းလဲပါ။

### ဒေတာဘေ့စ်ချိတ်ဆက်မှုအမှားများ

အက်ပ်က PostgreSQL သို့မချိတ်ဆက်နိုင်ပါက-

- `.env` ရှိ `PG_PASSWORD` သည် container ကိုပထမဆုံးဖန်တီးစဉ်ကအသုံးပြုခဲ့သည့်အတိုင်းဖြစ်ကြောင်းစစ်ဆေးပါ
- PostgreSQL container ကျန်းမာနေကြောင်းစစ်ဆေးပါ: `docker compose ps`
- စကားဝှက်ကိုပြောင်းလဲပြီးပါက volume ကိုဖယ်ရှားပြီးပြန်လည်ဖန်တီးရန်လိုအပ်နိုင်သည်: `docker compose down -v && docker compose up -d`

### Strfry relay ချိတ်ဆက်မှုမရှိခြင်း

WebSocket relay သည် အဓိကဝန်ဆောင်မှုတစ်ခုဖြစ်ပြီး ချန်လှပ်၍မရပါ။ Relay အလုပ်မလုပ်ပါက-

```bash
# Relay အခြေအနေစစ်ဆေးရန်
docker compose logs WebSocket relay

# Relay ကိုပြန်လည်စတင်ရန်
docker compose restart WebSocket relay
```

Relay စတင်ရန်ပျက်ကွက်ပါက port 7777 ပဋိပက္ခ သို့မဟုတ် ဒေတာလမ်းညွှန်တွင် ခွင့်ပြုချက်မလုံလောက်မှုရှိမရှိစစ်ဆေးပါ။

### RustFS / S3 သိုလှောင်မှုအမှားများ

- `STORAGE_ACCESS_KEY` နှင့် `STORAGE_SECRET_KEY` မှန်ကန်ကြောင်းစစ်ဆေးပါ
- RustFS container အလုပ်လုပ်နေကြောင်းစစ်ဆေးပါ: `docker compose ps rustfs`
- `http://localhost:9001` တွင် RustFS console ကိုဝင်ရောက်၍ bucket ဖန်တီးမှုကိုစစ်ဆေးပါ

## Cloudflare ဖြန့်ကျက်မှုပြဿနာများ

### Durable Object အမှားများ

**"Durable Object ရှာမတွေ့" သို့မဟုတ် binding အမှားများ-**

- DO bindings များမှန်ကန်ကြောင်းသေချာစေရန် `bun run deploy` (ဘယ်တော့မှ `wrangler deploy` ကိုတိုက်ရိုက်မသုံးပါနှင့်) ကိုသုံးပါ
- `wrangler.jsonc` တွင် DO အတန်းအမည်များနှင့် bindings များမှန်ကန်ကြောင်းစစ်ဆေးပါ
- DO အသစ်တစ်ခုထည့်ပြီးနောက် ၎င်းကိုမရရှိနိုင်မီ ဖြန့်ကျက်ရမည်

**DO သိုလှောင်မှုကန့်သတ်ချက်များ-**

Cloudflare Durable Objects များသည် key-value တစ်စုံလျှင် 128 KB ကန့်သတ်ချက်ရှိသည်။ သိုလှောင်မှုအမှားများတွေ့ပါက-

- မှတ်စုပါအကြောင်းအရာသည် ကန့်သတ်ချက်မကျော်လွန်ကြောင်းသေချာပါစေ (ပူးတွဲမှုများစွာပါသောအလွန်ကြီးမားသောမှတ်စုများ)
- ECIES စာအိတ်များကို ထပ်ခါမလုပ်မိကြောင်းစစ်ဆေးပါ

### Worker အမှားများ (500 တုံ့ပြန်မှုများ)

Worker မှတ်တမ်းများကိုစစ်ဆေးပါ-

```bash
bunx wrangler tail
```

အဖြစ်များသော အကြောင်းရင်းများ-
- ပျောက်ဆုံးနေသော secrets (အတည်ပြုရန် `bunx wrangler secret list` ကိုသုံးပါ)
- မှားယွင်းသော `ADMIN_PUBKEY` ပုံစံ (64 hex စာလုံးဖြစ်ရမည်၊ `npub` ရှေ့ဆွဲမပါ)
- အခမဲ့အဆင့်တွင် နှုန်းကန့်သတ်ချက် (Workers Free တွင် တစ်မိနစ်လျှင် တောင်းဆိုမှု ၁၀၀၀)

### "Pages deploy" အမှားများဖြင့် ဖြန့်ကျက်မှုပျက်ကွက်ခြင်း

`wrangler pages deploy` သို့မဟုတ် `wrangler deploy` ကိုတိုက်ရိုက်ဘယ်တော့မှမသုံးပါနှင့်။ အမြဲတမ်း root `package.json` scripts များကိုသုံးပါ-

```bash
bun run deploy          # အားလုံးကိုဖြန့်ကျက်ရန် (အက်ပ် + မားကတ်တင်းဆိုဒ်)
bun run deploy:site     # မားကတ်တင်းဆိုဒ်ကိုသာဖြန့်ကျက်ရန်
```

လမ်းညွှန်မှားယွင်းမှ `wrangler pages deploy dist` ကိုသုံးခြင်းသည် Vite အက်ပ်တည်ဆောက်မှုကို Astro ဆိုဒ်အစား Pages သို့ဖြန့်ကျက်စေပြီး 404 အမှားများဖြင့် မားကတ်တင်းဆိုဒ်ကိုပျက်စီးစေသည်။

## ဒက်စ်တော့အက်ပ်ပြဿနာများ

### အလိုအလျောက်အပ်ဒိတ်အလုပ်မလုပ်ခြင်း

ဒက်စ်တော့အက်ပ်သည် ဗားရှင်းအသစ်များကိုစစ်ဆေးရန် Tauri updater ကိုအသုံးပြုသည်။ အပ်ဒိတ်များကိုရှာမတွေ့ပါက-

- သင်၏အင်တာနက်ချိတ်ဆက်မှုကိုစစ်ဆေးပါ
- အပ်ဒိတ် endpoint သို့ရောက်ရှိနိုင်ကြောင်းစစ်ဆေးပါ: `https://github.com/rhonda-rodododo/llamenos-platform/releases/latest/download/latest.json`
- Linux တွင် AppImage အလိုအလျောက်အပ်ဒိတ်သည် ၎င်း၏လမ်းညွှန်တွင် ဖိုင်အားရေးခွင့်ရှိရန်လိုအပ်သည်
- macOS တွင် အက်ပ်သည် `/Applications` အတွင်းတွင်ရှိရမည် (DMG မှတိုက်ရိုက်အလုပ်မလုပ်ပါ)

လက်ဖြင့်အပ်ဒိတ်လုပ်ရန် [ဒေါင်းလုဒ်](/download) စာမျက်နှာမှ နောက်ဆုံးထွက်ရှိမှုကိုဒေါင်းလုဒ်လုပ်ပါ။

### PIN သော့ဖွင့်မှုပျက်ကွက်ခြင်း

ဒက်စ်တော့အက်ပ်တွင် သင့် PIN ကိုငြင်းပယ်ခံရပါက-

- မှန်ကန်သော PIN ကိုထည့်သွင်းကြောင်းသေချာပါစေ ("PIN မေ့သွားသည်" ပြန်လည်ရယူခြင်းမရှိပါ)
- PIN များသည် စာလုံးများပါပါက case-sensitive ဖြစ်သည်
- သင်၏ PIN ကိုမေ့သွားပါက အသစ်တစ်ခုသတ်မှတ်ရန် သင့် nsec ကိုပြန်လည်ထည့်သွင်းရမည်။ သင်၏ကုဒ်ဝှက်ထားသောမှတ်စုများသည် သင်၏အထောက်အထားနှင့်ချိတ်ဆက်ထားသောကြောင့် PIN နှင့်မဟုတ်သောကြောင့် ၎င်းတို့ကိုဆက်လက်ဝင်ရောက်နိုင်ဆဲဖြစ်သည်
- Tauri Stronghold သည် သင်၏ nsec ကို PIN-ဆင်းသက်သော့ (PBKDF2) ဖြင့်ကုဒ်ဝှက်သည်။ မှားယွင်းသော PIN သည် အမှားသတင်းစကားမဟုတ်ဘဲ မမှန်ကန်သောကုဒ်ဖော်မှုကိုထုတ်ပေးသည် — အက်ပ်သည် ဆင်းသက်လာသောအများသုံးသော့ကိုစစ်ဆေးခြင်းဖြင့် ၎င်းကိုရှာဖွေတွေ့ရှိသည်

### သော့ပြန်လည်ရယူခြင်း

သင့်စက်ပစ္စည်းသို့ဝင်ရောက်ခွင့်ပျောက်ဆုံးသွားပါက-

၁။ သင့် nsec (စကားဝှက်မန်နေဂျာတွင်သိမ်းဆည်းထားသင့်သည်) ကိုအသုံးပြု၍ စက်ပစ္စည်းအသစ်တွင်အကောင့်ဝင်ပါ
၂။ WebAuthn passkey ကိုမှတ်ပုံတင်ထားပါက ၎င်းကိုအစားထိုးအသုံးပြုနိုင်သည်
၃။ သင်၏ကုဒ်ဝှက်ထားသောမှတ်စုများကိုဆာဗာဘက်ခြမ်းတွင်သိမ်းဆည်းထားသည် — တူညီသောအထောက်အထားဖြင့်အကောင့်ဝင်သည်နှင့် ၎င်းတို့ကိုကုဒ်ဖော်နိုင်သည်
၄။ nsec နှင့် passkey နှစ်ခုလုံးပျောက်ဆုံးသွားပါက သင့်အက်ဒမင်ကိုဆက်သွယ်ပါ။ ၎င်းတို့သည် သင့် nsec ကိုပြန်လည်ရယူနိုင်မည်မဟုတ်သော်လည်း သင့်အတွက်အထောက်အထားအသစ်တစ်ခုဖန်တီးနိုင်သည်။ သင့်အထောက်အထားဟောင်းအတွက်ကုဒ်ဝှက်ထားသောမှတ်စုများကို သင်ထပ်မံဖတ်နိုင်တော့မည်မဟုတ်ပါ

### အက်ပ်မစတင်ပါ (ဗလာဝင်းဒိုး)

- သင့်စနစ်သည်အနည်းဆုံးလိုအပ်ချက်များနှင့်ကိုက်ညီကြောင်းစစ်ဆေးပါ ([ဒေါင်းလုဒ်](/download) ကိုကြည့်ပါ)
- Linux တွင် WebKitGTK တပ်ဆင်ထားကြောင်းသေချာပါစေ: `sudo apt install libwebkit2gtk-4.1-0` (Debian/Ubuntu) သို့မဟုတ် အညီအမျှ
- terminal မှစတင်၍ အမှားထွက်ပေါက်ကိုကြည့်ရှုရန်ကြိုးစားပါ: `./llamenos` (AppImage) သို့မဟုတ် စနစ်မှတ်တမ်းများကိုစစ်ဆေးပါ
- Wayland ကိုအသုံးပြုပါက `GDK_BACKEND=x11` ဖြင့်စမ်းသပ်ကြည့်ပါ

### တစ်ခုတည်းသော instance ပဋိပက္ခ

Llámenos သည် တစ်ခုတည်းသော instance mode ကိုကျင့်သုံးသည်။ အက်ပ်ကအလုပ်လုပ်နေပြီဟုဆိုသော်လည်း ဝင်းဒိုးကိုရှာမတွေ့ပါက-

- နောက်ခံလုပ်ငန်းစဉ်များကိုစစ်ဆေးပါ: `ps aux | grep llamenos`
- မိဘမဲ့လုပ်ငန်းစဉ်များကိုသတ်ပါ: `pkill llamenos`
- Linux တွင် သက်တမ်းလွန်သော့ခတ်ဖိုင်ရှိမရှိစစ်ဆေးပြီး အက်ပ်ပျက်ကျပါက ၎င်းကိုဖယ်ရှားပါ

## မိုဘိုင်းအက်ပ်ပြဿနာများ

### ထောက်ပံ့ခြင်းပျက်ကွက်မှုများ

အသေးစိတ် ထောက်ပံ့ခြင်းပြဿနာဖြေရှင်းခြင်းအတွက် [မိုဘိုင်းလမ်းညွှန်](/docs/mobile-guide#troubleshooting-mobile-issues) ကိုကြည့်ပါ။

အဖြစ်များသော အကြောင်းရင်းများ:
- QR ကုဒ်သက်တမ်းကုန်ခြင်း (token များသည် ၅ မိနစ်အကြာတွင်သက်တမ်းကုန်သည်)
- စက်ပစ္စည်းနှစ်ခုလုံးတွင် အင်တာနက်ချိတ်ဆက်မှုမရှိခြင်း
- ဒက်စ်တော့အက်ပ်နှင့်မိုဘိုင်းအက်ပ်တို့သည် မတူညီသောပရိုတိုကောဗားရှင်းများကိုအသုံးပြုနေခြင်း

### Push အကြောင်းကြားချက်များရောက်မလာခြင်း

- OS ဆက်တင်များတွင် အကြောင်းကြားချက်ခွင့်ပြုချက်များပေးထားကြောင်းစစ်ဆေးပါ
- Android တွင် ဘက်ထရီအကောင်းဆုံးပြုလုပ်မှုက အက်ပ်ကိုနောက်ခံတွင်မသတ်ပစ်ကြောင်းစစ်ဆေးပါ
- iOS တွင် Llámenos အတွက် Background App Refresh ဖွင့်ထားကြောင်းစစ်ဆေးပါ
- သင့်တွင် တက်ကြွသောအလုပ်ချိန်ရှိပြီး အနားယူချိန်မဟုတ်ကြောင်းစစ်ဆေးပါ

## တယ်လီဖုန်းပြဿနာများ

### Twilio webhook ဖွဲ့စည်းမှု

ခေါ်ဆိုမှုများကိုစေတနာ့ဝန်ထမ်းများသို့လမ်းကြောင်းမသတ်မှတ်ပါက-

၁။ Twilio console တွင် သင့် webhook URL များမှန်ကန်ကြောင်းစစ်ဆေးပါ-
   - Voice webhook: `https://your-worker.your-domain.com/telephony/incoming` (POST)
   - Status callback: `https://your-worker.your-domain.com/telephony/status` (POST)
၂။ သင့်ဆက်တင်များရှိ Twilio အထောက်အထားများ console နှင့်ကိုက်ညီမှုရှိမရှိစစ်ဆေးပါ-
   - Account SID
   - Auth Token
   - ဖုန်းနံပါတ် (နိုင်ငံကုဒ်ပါဝင်ရမည်၊ ဥပမာ `+1234567890`)
၃။ Twilio debugger တွင် အမှားများကိုစစ်ဆေးပါ: [twilio.com/console/debugger](https://www.twilio.com/console/debugger)

### နံပါတ်တည်ဆောက်မှု

- ဖုန်းနံပါတ်သည် Twilio ပိုင်ဆိုင်သောနံပါတ် သို့မဟုတ် အတည်ပြုထားသော ခေါ်ဆိုသူ ID ဖြစ်ရမည်
- ဒေသခံဖွံ့ဖြိုးတိုးတက်ရေးအတွက် Cloudflare Tunnel သို့မဟုတ် ngrok ကိုသုံး၍ သင့်ဒေသခံ Worker ကို Twilio သို့ထုတ်ဖော်ပြပါ
- နံပါတ်၏ Voice ဖွဲ့စည်းမှုသည် ပုံသေ TwiML Bin မဟုတ်ဘဲ သင့် webhook URL ကိုညွှန်ပြကြောင်းစစ်ဆေးပါ

### ခေါ်ဆိုမှုများချိတ်ဆက်သော်လည်း အသံမရှိခြင်း

- တယ်လီဖုန်းဝန်ဆောင်မှုပေးသူ၏ မီဒီယာဆာဗာများသည် စေတနာ့ဝန်ထမ်း၏ဖုန်းသို့ရောက်ရှိနိုင်ကြောင်းသေချာပါစေ
- RTP အသွားအလာကိုပိတ်ဆို့နေသော NAT/firewall ပြဿနာများကိုစစ်ဆေးပါ
- WebRTC ကိုအသုံးပြုပါက STUN/TURN ဆာဗာများမှန်ကန်စွာဖွဲ့စည်းထားကြောင်းစစ်ဆေးပါ
- အချို့ VPN များသည် VoIP အသွားအလာကိုပိတ်ဆို့သည် — VPN မပါဘဲစမ်းကြည့်ပါ

### SMS/WhatsApp မက်ဆေ့ချ်များရောက်မလာခြင်း

- မက်ဆေ့ချ် webhook URL များကို သင့်ဝန်ဆောင်မှုပေးသူ၏ console တွင် မှန်ကန်စွာဖွဲ့စည်းထားကြောင်းစစ်ဆေးပါ
- WhatsApp အတွက် Meta webhook အတည်ပြုချက် token သည် သင့်ဆက်တင်များနှင့်ကိုက်ညီမှုရှိမရှိသေချာပါစေ
- **အက်ဒမင်ဆက်တင်များ > ချန်နယ်များ** တွင် မက်ဆေ့ချ်ချန်နယ်ကိုဖွင့်ထားကြောင်းစစ်ဆေးပါ
- Signal အတွက် signal-cli bridge အလုပ်လုပ်နေပြီး သင့် webhook သို့ထပ်ဆင့်ပို့ရန်ဖွဲ့စည်းထားကြောင်းစစ်ဆေးပါ

## ကုဒ်ဝှက်ဆိုင်ရာအမှားများ

### သော့မကိုက်ညီမှုအမှားများ

**မှတ်စုများဖွင့်သောအခါ "ကုဒ်ဖော်၍မရ" သို့မဟုတ် "သော့မမှန်ကန်"-**

- ၎င်းသည် များသောအားဖြင့် မှတ်စုကို သင်အကောင့်ဝင်ထားသည့်အထောက်အထားနှင့်မတူသော အခြားအထောက်အထားတစ်ခုအတွက်ကုဒ်ဝှက်ထားခြင်းကြောင့်ဖြစ်သည်
- သင်မှန်ကန်သော nsec ကိုအသုံးပြုနေကြောင်းစစ်ဆေးပါ (ဆက်တင်များရှိ သင့် npub သည် အက်ဒမင်မြင်သည့်အတိုင်းဖြစ်မဖြစ်စစ်ဆေးပါ)
- သင်မကြာသေးမီကသင့်အထောက်အထားကိုပြန်လည်ဖန်တီးခဲ့ပါက သင့်ယခင်အများသုံးသော့အတွက်ကုဒ်ဝှက်ထားသောမှတ်စုဟောင်းများကို သော့အသစ်ဖြင့်ကုဒ်ဖော်၍မရနိုင်ပါ

**အကောင့်ဝင်ချိန်တွင် "လက်မှတ်မမှန်ကန်"-**

- nsec သည် ပျက်စီးနေနိုင်သည် — သင့်စကားဝှက်မန်နေဂျာမှ ၎င်းကိုပြန်လည်ထည့်သွင်းကြည့်ပါ
- nsec အပြည့်အစုံကိုကူးထည့်ထားကြောင်းသေချာပါစေ (`nsec1` ဖြင့်စတင်သည်၊ စုစုပေါင်းစာလုံး ၆၃ လုံး)
- ပိုနေသော နေရာလွတ် သို့မဟုတ် စာကြောင်းသစ်စာလုံးများကိုစစ်ဆေးပါ

### လက်မှတ်အတည်ပြုချက်ပျက်ကွက်မှုများ

Hub ဖြစ်ရပ်များ လက်မှတ်အတည်ပြုချက်ပျက်ကွက်ပါက-

- စနစ်နာရီကိုထပ်တူပြုထားကြောင်းစစ်ဆေးပါ (NTP)။ နာရီအချိန်ကွာခြားမှုကြီးမားပါက ဖြစ်ရပ်အချိန်တံဆိပ်များတွင် ပြဿနာဖြစ်စေနိုင်သည်
- WebSocket relay သည် အမည်မသိ pubkeys များမှဖြစ်ရပ်များကိုထပ်ဆင့်မပို့ကြောင်းစစ်ဆေးပါ
- လက်ရှိ hub အဖွဲ့ဝင်စာရင်းကိုပြန်လည်ရယူရန် အက်ပ်ကိုပြန်လည်စတင်ပါ

### ECIES စာအိတ်အမှားများ

**မှတ်စုကုဒ်ဖော်ချိန်တွင် "သော့ကိုဖြေရန်"မရ"-**

- ECIES စာအိတ်ကို မှားယွင်းသော အများသုံးသော့ဖြင့်ဖန်တီးထားနိုင်သည်
- အက်ဒမင်က pubkey တွင် စာလုံးပေါင်းမှားပြီး စေတနာ့ဝန်ထမ်းတစ်ဦးကိုထည့်သွင်းပါက ၎င်းဖြစ်နိုင်သည်
- အက်ဒမင်သည် စေတနာ့ဝန်ထမ်း၏ အများသုံးသော့ကိုစစ်ဆေးပြီး လိုအပ်ပါက ပြန်လည်ဖိတ်ကြားသင့်သည်

**"ciphertext အလျားမမှန်ကန်"-**

- ၎င်းသည် ဒေတာပျက်စီးမှုကိုညွှန်ပြသည်၊ ဖြစ်နိုင်သည်မှာ ဖြတ်တောက်ထားသောကွန်ရက်တုံ့ပြန်မှုကြောင့်ဖြစ်သည်
- လုပ်ဆောင်ချက်ကိုပြန်လုပ်ပါ။ ဆက်လက်ဖြစ်ပေါ်နေပါက ကုဒ်ဝှက်ထားသောဒေတာသည် အပြီးတိုင်ပျက်စီးသွားနိုင်သည်
- တုံ့ပြန်မှုကိုယ်ထည်များကိုဖြတ်တောက်နိုင်သော proxy သို့မဟုတ် CDN ပြဿနာများကိုစစ်ဆေးပါ

### Hub သော့အမှားများ

**"hub ဖြစ်ရပ်ကိုကုဒ်ဖော်၍မရ"-**

- သင်နောက်ဆုံးချိတ်ဆက်ပြီးနောက် hub သော့ကိုလှည့်ပြောင်းထားနိုင်သည်
- နောက်ဆုံး hub သော့ကိုရယူရန် အက်ပ်ကိုပိတ်ပြီးပြန်ဖွင့်ပါ
- သင်မကြာသေးမီက hub မှဖယ်ရှားခံရပြီးပြန်ထည့်သွင်းခံရပါက သင့်မရှိစဉ်အတွင်း သော့လှည့်ပြောင်းသွားနိုင်သည်

## အကူအညီရယူခြင်း

သင့်ပြဿနာကိုဤနေရာတွင်ဖော်ပြမထားပါက-

- သိရှိထားသော bugs များနှင့် အလုပ်ဖြေရှင်းနည်းများအတွက် [GitHub Issues](https://github.com/rhonda-rodododo/llamenos-platform/issues) ကိုစစ်ဆေးပါ
- အသစ်တစ်ခုမဖန်တီးမီ ရှိပြီးသားပြဿနာများကိုရှာဖွေပါ
- bug တစ်ခုကိုအစီရင်ခံသောအခါ သင့်ဖြန့်ကျက်မှုပုံစံ (Cloudflare/Docker/Kubernetes)၊ ပလက်ဖောင်း (Desktop/Mobile) နှင့် ဘရောက်ဆာ console သို့မဟုတ် terminal မှ အမှားသတင်းစကားများထည့်သွင်းပါ
