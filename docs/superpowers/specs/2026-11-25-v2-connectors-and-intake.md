# v2 connectors: principals, manifest and the intake inbox

**Date:** 2026-11-25 · **Base:** `origin/main` @ `bf99f880d` · **Epic:** #2977, stages 1 and 2
**Issues:** #2939 (connector principals), #2940 (intake inbox), #2942 (firehose port, the first consumer)
**Builds on:**
- the v2 wire format (PR #2996, signed off 2026-11-24): the hub authority chain links, the D10 canonical profile, D12 with the §5.5 answer (permission ids in clear), and D16;
- the v2 files spec (PR #3007, signed off 2026-11-25): raw-source evidence is a v2 file;
- the reader groups in #2961 and the hub chain in #2963.

**Status:** DRAFT for operator decisions C1–C11.

Stages 3 and 4 of #2977 (releases, #2941; reference collections, #2945) get their own spec. This
one fixes the parts they build on, and reserves their manifest fields now so the manifest format
does not change when they land (§4.3).

**The rule this serves (#2977):** nothing leaves an instance except what a human released,
minimised, to a destination the hub enrolled. No shared service ever sees a hotline's calls,
messages or members (#2369). External systems connect as enrolled, revocable, non-human
principals, never through server-held keys.

## 0. Decisions at a glance

| # | Decision | Recommendation | § |
|---|---|---|---|
| C1 | What a connector is to the server | **A separate principal kind with its own table, routes and middleware.** A connector key never authenticates as a user, and a user key never reaches a connector route | 2 |
| C2 | How a connector enrolls | **The admin's client issues a one-time enrollment code** (room, token, a 32-byte secret and a chain anchor). The operator pastes it on the connector host. The request travels sealed under the secret, and the admin appends `connector_enroll` | 3 |
| C3 | Manifest shape | **Two parts.** A *core* in the D10 profile, which the server stores and enforces, and a *private* part (hosts, description, agents) that only the connector host and the approving admin see. `manifestHash` commits to both | 4 |
| C4 | Connector capabilities | **From the manifest core, not from roles.** No `integration:*` scope for connectors enters `PERMISSION_CATALOG`, so no role can ever carry one by mistake | 5 |
| C5 | Changing a manifest or rotating keys | **A new `connector_enroll` link for the same connector id.** The latest one is in force. The HMAC key carries over | 3.4 |
| C6 | Who reads intake | **A new reader purpose, `intake`** (permission `intake:review`, held by the admin roles by default), so a hub can delegate triage without making the reviewers admins | 6.2 |
| C7 | Dedup | **A per-revision tag the server can't link across revisions** (UNIQUE per connector). The stable source HMAC lives only inside the sealed tier | 6.4 |
| C8 | Revocation and writes | Items naming a head **at or after** the revocation are invalid. Unconfirmed items from **before** it are flagged, and the revoking admin may discard them in one step | 7 |
| C9 | Confirming an item | **The reviewer's client creates the record.** The raw source moves to the record as evidence (a header re-wrap, same blob), and the intake item becomes a tombstone | 6.5 |
| C10 | Abuse limits | A per-connector item rate and byte quota as hub policy, plus a per-item size cap | 6.6 |
| C11 | SDK and runtime | **One implementation: a crate module**, exposed through the existing server binding for non-Rust hosts. One connector per isolation boundary. Keys live on the connector host only | 8 |

## 1. Today, measured (summary)

Surveyed against `origin/main` @ `bf99f880d`.

- **Every authenticated request resolves to a `User`** (`apps/worker/lib/auth.ts:192-260`). There is no non-human principal. The only non-human actors are the audit's `actorPubkey = 'system'` and the firehose agent.
- **The firehose agent's key is generated by the server**, sealed with a deploy secret (`firehose_connections.encrypted_agent_nsec`, `apps/worker/db/schema/firehose.ts:33-35`), and unsealed in-process (`apps/worker/services/firehose-agent.ts`).
- **Group messages reach the worker in plaintext** and are handed to the firehose observer there (`apps/worker/messaging/router.ts:314`, `firehose-observer.ts`), which encrypts them afterwards. Inference runs in the worker.
- **Its output is a conversation** with `metadata.type = 'report'`, sealed to the agent and the hub's admins. Any later inbound integration would have to reinvent this path.
- The firehose has its own permissions (`firehose:read`, `firehose:manage`, `packages/shared/permissions.ts:186-187`) and four tables. #2942 deletes all of it.
- The Ed25519 bearer token signs `(pubkey, timestamp, method, path, nonce)` and is single-use (`auth.ts:139-160`). It does not cover the body. That is fine for this design, because every connector write carries its own signature over its content (§6.3).

## 2. C1: a connector is its own principal kind — OPERATOR DECISION

**Shape.**

- A table `hub_connectors(hub_id, connector_id, signing_pk, manifest_core jsonb, manifest_hash, enrolled_seq, revoked_seq)`.
  It is a **cache of chain state**, written when a `connector_enroll` or `connector_revoke` link is appended. Clients never trust it (#2963).
- Connector routes live under `/api/hubs/:hubId/connector/…`, behind their own middleware. That middleware resolves the bearer key against `hub_connectors` only, and refuses with the same uniform 401 when `revoked_seq` is set.
- The user middleware resolves against `users` only. A connector's key has no user row, so every existing route refuses it as `unregistered_pubkey` by construction. No route needs a new check.
- The auth result becomes a discriminated union, `{kind: 'user', …} | {kind: 'connector', hub, connectorId, manifestCore}`. Handlers type-check against the kind they accept.

**Why not a user row with a flag.** Every route that forgets the flag would become a connector
route. The separate table makes "a connector can call X" something that is written down, never
something left out.

**What a connector can do at all**, which is the whole route list for stages 1 and 2:

| Route | Purpose |
|---|---|
| `GET /hub-chain?after=<seq>` | Follow the hub chain forward from its anchor (the same endpoint clients use) |
| `GET /groups/:group/epoch` | The current epoch of a group it seals to, which it verifies against the chain |
| `POST /connector/intake` | Create an intake item (§6) |
| `PUT /connector/files/:fileId/segments/:n`, `POST …/complete` | Upload an item's raw source (files spec F4) |

There is no read, list or delete route for intake, including for the connector's own items. Stage 3
adds release fetch and acknowledgement. Stage 4 adds reference-collection sync.

## 3. C2: enrollment — OPERATOR DECISION

### 3.1 Who does what

- **The instance operator** registers the destinations a hub may use, out of band, in deploy config (§4.4). The operator also deploys the connector host.
- **A hub member with role management** approves the enrollment, because the wire spec's §5.4 requires role management for `connector_*` links.
- **`integration:manage`** (a new human permission, in the admin roles by default) covers what is not a chain link: inbound type allow-lists within the manifest, the hub-chosen alias, quotas (C10), and later the release profiles.

### 3.2 The handshake

It reuses the provisioning-room transport (`POST /api/provision/rooms`, PROTOCOL §6.8), with the
roles reversed from device linking. **The trusted side issues the code, and the headless side
consumes it.** A headless host can't scan a QR code, and the anchor has to come from a trusted
device (#2963 §3).

1. **The admin's client** opens a room and shows an enrollment code:
   `llamenos-connector://enroll?r=<room>&t=<token>&s=<secret>&h=<hub>&a=<seq>.<hash>`.
   - `secret` is 32 random bytes and never goes to the server.
   - `a` is the admin device's current *verified* hub head.
   - The room lives for 10 minutes and is single-use, like provisioning rooms.
2. **The operator** runs `connector enroll '<code>'` on the connector host. It does four things:
   - It generates, on the host: an Ed25519 signing key; a KEM keypair of the hub's current `crypto_format` suite (D16), whose format it learns from the anchored chain, not from the server; and, on first enrollment only, a 32-byte HMAC key (C5, §6.4).
   - It builds the request `R = {v: 1, hub, connector (16 random bytes, hex), signingPk, format, encryptionPk, manifestCore, manifestPrivate}` and signs it with the new signing key (proof of possession).
   - It seals `R` under `AEAD(HKDF(secret, L_CONNECTOR_ENROLL), AAD = lp(hub) ‖ lp(room))` and posts it to the room.
   - It pins the anchor `a`.
3. **The admin's client** opens `R`, checks the signature, and shows the full manifest (§4), including the real destination hosts from the private part.
4. **On approval,** the client appends two links in one compare-and-set sequence:
   - `connector_enroll {connector, signingPk, format, encryptionPk, manifestHash}`;
   - `group_epoch {group, kind: connector, subject: connector, epoch: 1, format, pk: encryptionPk, reason: create}`.
5. **The connector** follows the chain forward from `a`, verifying every link. It considers itself enrolled when it sees its own `connector_enroll` with the `manifestHash` it computed. No reply message is needed.

**Properties.**

- The server sees `R` only as ciphertext, so the destination hosts never reach it (#2939, review point 1).
- A server that substitutes the anchor or the chain is caught. The anchor came from the admin, and every later link must chain from it.
- A server that substitutes `R` can't produce a valid AEAD under the secret.
- **Residual:** whoever carries the code between the admin and the operator can enroll a connector of their own. The code is a credential, short-lived and single-use, and the approval screen shows the manifest the admin is agreeing to. Say so in the UI.

### 3.3 Why not the device-linking direction

In device linking, the new device shows the code and the primary scans it. Keeping that direction
here would need either a QR on a headless host, or a SAS comparison to stop the server from
swapping the admin's ephemeral key and reading `R`. The reversed code is shorter, needs no SAS,
and uses a symmetric secret, so it has no post-quantum gap (D16).

### 3.4 C5: manifest changes and key rotation — OPERATOR DECISION

- **Recommended:** a new `connector_enroll` link for the **same** `connector` id is valid, and the latest one is in force. It carries the new `manifestHash`, and new keys if they are being rotated. A key rotation also appends a `group_epoch` for `connector:<id>` with `epoch + 1`.
- The HMAC key is **not** in the chain. It carries over on the host, so dedup survives (#2940, update 2026-11-23).
- The inbox, the alias and the quota stay attached to the id. The audit shows "manifest changed", with a diff the admin's client renders.
- Contract note: the wire spec's §5.6 doesn't yet say whether a second `connector_enroll` for an id is valid. This spec adds that rule. A `connector_enroll` for a revoked id stays invalid. A revoked connector re-enrolls under a new id.
- **Alternative:** revoke and enroll a new id each time. That is simpler to validate, but the item history splits across ids, and dedup state has to be migrated by hand.

## 4. C3: the manifest — OPERATOR DECISION

### 4.1 Two parts, one commitment

```
manifestHash = H( lp(utf8(L_CONNECTOR_MANIFEST)) ‖ H(utf8(canonical(core))) ‖ H(privateBytes) )
```

- **`core`** is in the D10 profile: sorted keys, no free text, ids and enum words only. The server stores it in clear and enforces it. It is canonicalised only in the crate.
- **`private`** is an opaque UTF-8 JSON document, committed by the hash of its exact bytes, so it needs no canonical form. It holds free text and hosts, and lives only on the connector host and on the approving admin's screen.

### 4.2 Core (server-enforced)

| Field | Meaning | Enforced by |
|---|---|---|
| `v` | Manifest version, `1` | crate |
| `ingest` | Sorted entity type refs (#2938 definition ids) the connector may create intake items of | server, on every intake write |
| `destinations` | Sorted opaque destination ids from the operator registry, such as `dest-3` | server, at enrollment (§4.4); the connector runtime, on egress |
| `releases` | Reserved for stage 3: release profile ids it may consume. Must be empty until #2941 lands | server |
| `references` | Reserved for stage 4: reference collection ids it maintains. Must be empty until #2945 lands | server |
| `limits` | Optional caps the connector asks for, below the hub policy (C10) | server |

### 4.3 Private (shown to the approving admin, never stored on the server)

- `description`: operator-facing free text.
- `destinations`: for each id in the core, the real endpoint, port and pinned CA fingerprint as the connector host has them configured.
- `agents[]` (#2939, comment 1): `task`; output types, which must be a subset of `core.ingest`, checked by the crate; the model name, pinned content hash and quantisation; the runtime name and pinned hash (internal review F5: the runtime is code); and `placement: connector-local`, the only value accepted.
- `sources`: the inbound sources the connector watches, described for the admin.

**Agents are private, not core,** because the server enforces nothing about them. Their output is
bounded by `core.ingest`, which the server does enforce. Keeping model and source details off the
server avoids another plaintext list of what this instance runs.

### 4.4 The operator registry: two halves

- **Server half** (deploy config): `CONNECTOR_DESTINATIONS = [{id, hubs: [...]}]`. Ids and permitted hubs only. The server refuses a `connector_enroll` append whose core names a destination not registered for that hub.
- **Connector-host half** (deploy config on that host): each id's endpoint, CA and credentials. Partner-issued credentials stay on the host and never enter the database.

The admin's approval screen checks that every private destination matches a core id. It does not
need the registry itself: what the host *will* talk to is the private part, and the admin approves
exactly that.

## 5. C4: capabilities come from the manifest, not from roles — OPERATOR DECISION

#2939 proposed `integration:ingest`, `integration:release-consume` and `integration:reference-sync`
as catalog scopes that no default role carries.

- **Recommended:** don't add them. A connector's capabilities are `core.ingest`, `core.releases` and `core.references`, committed in the chain by `manifestHash`. They are evaluated on connector routes only.
- A permission string that only connectors should hold, sitting in the same catalog that custom roles draw from, is one role edit away from a human holding it. Here no such string exists.
- **Human permissions:** `integration:manage` (§3.1) and `intake:review` (C6). Stage 3 adds `records:release`.
- `firehose:read` and `firehose:manage` are deleted with #2942.

## 6. The intake inbox (#2940)

### 6.1 Shape

An intake item is a document of the system type `intake` in the generic sealed store (#2961).
`doc_id` is chosen by the connector, which makes writes idempotent the same way as file uploads (F4).

| Tier | Holds | Readers |
|---|---|---|
| `item` | The draft (field values of the `type` it names), provenance (§6.3), the trust label, and the stable source HMAC | the `intake` purpose group (C6) |

Plaintext columns: `hub`, `doc_id`, `connector_id`, `type_ref`, `dedup_tag` (§6.4), `hub_head_seq`,
`state` (`new` \| `confirmed` \| `merged` \| `discarded`), `received_at` (to the hour), and the
connector signature.

**Raw source** is a v2 file whose parent is the intake item (F1), so it inherits the `intake`
group. It is uploaded by the connector and signed with the connector's key, which stands in for
F6's uploader device signature. Its F6 plaintext commitment is the integrity hash #2940 asks for.

**No index tokens.** The connector holds no index key, so intake items are never searchable on the
server. That is the "never indexed" rule for external identifiers, enforced by construction.
Reviewers search the inbox on their client. It is bounded by the retention in §6.5.

### 6.2 C6: the `intake` reader purpose — OPERATOR DECISION

- **Recommended:** add `intake: ['intake:review']` to `READER_PURPOSE_PERMISSIONS`. `intake:review` goes into the admin roles by default. The `intake` group is chain-signed like every purpose group, and the connector verifies its epoch key before sealing (#2963, "a server-substituted `admins` key is refused").
- This lets a hub hand triage to reviewers who are not admins. Today that would mean making them admins.
- **Alternative:** seal to `admins`, as #2940 first said. That is simpler, but every reviewer becomes an admin, which is the over-grant reader groups exist to stop.
- Because `intake` is a new purpose, it is a contract change (`ReaderPurpose` enum and vectors). It lands in this epic's contract PR, not as a patch.
- Every escrow setter must hold every purpose's permissions (`permissions.ts`, purpose table comment). `intake:review` joins that set.

### 6.3 The write

`POST /connector/intake` with `{docId, typeRef, dedupTag, hubHead: {seq, hash}, header, content, sig}`.

```
sig = Ed25519(connectorSigningKey, utf8(L_INTAKE_SIG) ‖ 0x00 ‖
        H( lp(hub) ‖ lp(docId) ‖ lp(typeRef) ‖ lp(dedupTag) ‖ u64(hubHead.seq) ‖ hubHead.hash ‖
           H(header) ‖ H(content) ))
```

**The server checks:** the connector isn't revoked; `typeRef ∈ core.ingest`; the item is within
quota (C10); `hubHead` is the current head or at most one link behind it (otherwise 409, and the
connector catches up and re-seals); `dedupTag` is unique; and `sig` verifies.

**The reviewer's client checks the same things from its own verified chain,** and does not take
the server's word for any of them:
- the connector was enrolled and active at `hubHead`;
- the header addresses the `intake` group's chain-signed epoch;
- `sig` verifies against the enrolled `signingPk`.

An item that fails any of these is shown as **invalid** and cannot be confirmed.

**Provenance inside the sealed tier:**
- the connector id;
- the source kind;
- `sourceHmac = HMAC(K_hmac, L_INTAKE_SOURCE ‖ sourceId)`, stable across revisions;
- the source's own timestamp;
- the received time;
- the trust label;
- for agent output: the model hash, prompt-template version and source window (#2939, comment 1).

**Trust labels:**
- `external`: everything that arrives through a connector;
- `machine-generated`: anything an agent drafted, shown in addition to `external`.

The volunteer-facing label is "External feed: <alias>". The alias is hub vocabulary, so it is
sealed under `members` (#2191). The connector never knows it.

### 6.4 C7: dedup without an update-frequency leak — OPERATOR DECISION

#2940's update accepted that matching HMACs show the server how often a source object changes.
This removes that leak at no cost.

```
dedupTag = HMAC(K_hmac, L_INTAKE_DEDUP ‖ lp(sourceId) ‖ H(normalisedSourceBytes))
```

- **The same object at the same revision** gives the same tag. The server refuses the duplicate with a 409, which the connector treats as success. This covers retries after a lost response, and a source that re-sends.
- **A new revision** gives an unrelated tag. The server can't link revisions to each other.
- Reviewers link revisions on their client through the stable `sourceHmac` in the sealed tier, and see "updated version of item …".
- The connector's local dedup state stays as #2939 described: HMACs only, with a TTL.

### 6.5 C9: confirming an item — OPERATOR DECISION

1. The reviewer's client opens the item, shows the draft beside the raw source, and lets the reviewer edit it.
2. It **creates a record** of the item's type, or **merges** the draft into an existing record. Either way it computes the record's index tokens under the field's searching-group index key (#2961 A5), which the connector never had.
3. **The raw source becomes the record's evidence.** The client re-wraps the file's header from the `intake` group to the record's evidence tier. The blob is untouched (F1, re-parenting). The record's sealed tier holds `derivedFrom: {intakeDoc, rawSourceFile, itemHash}`. That is the chain of custody, from the original bytes to the confirmed record.
4. The item's state becomes `confirmed` or `merged`, its `item` tier is deleted, and the row stays as a **tombstone**: state, connector, type, hour, and the hash the record names.
5. **Discard** deletes the tier and the raw-source file (F7), and leaves a tombstone.

**Retention.** The `intake` definition declares retention like every other type (#2186):
unresolved items expire after a hub-set period, and tombstones after the audit window. The numbers
belong to #2978. This spec requires only that `intake` never defaults to "keep forever".

### 6.6 C10: abuse limits — OPERATOR DECISION

A compromised connector, or a hostile source behind it, can flood the inbox. Triage contains bad
*content*. Volume needs limits.

- **Hub policy, per connector:** items per hour (suggested 120) and raw-source bytes per day (suggested 1 GiB). These count against the hub quota (F5).
- **Per item:** a draft tier of at most 256 KiB, and a raw source of at most the F5 per-file maximum.
- **Over the limit:** a 429. The admins see a "connector over its limit" notice. Nothing is dropped silently on the server side. What the connector does with the backlog is its own (bounded, TTL) state.
- `core.limits` can lower these values, never raise them.

## 7. C8: revocation, verified from the chain — OPERATOR DECISION

**Epic gate (#2977, stage 1):** "a revoked connector can't read or write anything, which is
verified from the chain, not from the server's word."

| | What enforces it | Verified from the chain? |
|---|---|---|
| **Reads** | Nothing is ever sealed to a connector except stage 3 releases, and clients refuse to seal a release to a `connector:<id>` group whose connector is revoked in their verified chain | **Yes.** A lying server can't make a client seal to a revoked connector |
| **Writes, after revocation** | An item whose `hubHead.seq` is at or above the `connector_revoke` link is invalid on every reviewer's client (§6.3) | **Yes** |
| **Writes that name an older head** | The server refuses the revoked key (C1), and refuses heads more than one link behind (§6.3) | No. This is the server's word, and it is the residual |

**The residual, stated.** A revoked connector that still holds its key, colluding with a server
that ignores both checks, can write items naming a head from before the revocation. This is the
same shape as D13's stale-signer window.

**Closing it on the client side:**
- When a client sees a `connector_revoke`, it marks every *unconfirmed* item from that connector **"from a connector since revoked"**. Confirming one takes an extra, explicit step.
- **The revoke dialog offers "discard all unconfirmed items from this connector".** That should be the default when the reason is "compromised".
- Confirmed records are unaffected. They were reviewed by a person, and their provenance still names the connector.

## 8. C11: SDK and runtime — OPERATOR DECISION

**One implementation.**

- A connector module in the shared crate covers: key generation, the enrollment client (§3.2), following and verifying the chain from a pinned anchor, verifying epoch keys, sealing intake items, signing, and the file sealer (reusing F2).
- Non-Rust connector hosts (the firehose host runs a Java messaging client, for example) use it through the existing server binding (`ffi_server`), not through a second implementation.
- The SDK refuses to seal unless the target epoch key verifies against the chain. There is no "skip verification" option, and no test-only build of one.

**Runtime posture (#2939, review points 2–4):**
- **One connector per isolation boundary.** Never co-locate two.
- A network namespace whose egress is only the private manifest's destinations, enforced by infrastructure.
- No database credentials and no `SERVER_SECRET`.
- Plaintext exists only in transit, and payloads are never logged.
- An encrypted disk, and no unencrypted swap.

**Keys** live in one file on the connector host, mode `0600`, on the encrypted volume: the signing
key, the KEM secret and the HMAC key. They are never in the database, never in deploy vars, and
never in a backup the server can read. Losing the file means re-enrolling under a new id; its
dedup state is lost with it, and that is stated.

**Agents** run as a separate unprivileged process with no access to the key file (internal review
F5). The process that holds the keys only receives drafts of allowed types.

## 9. The firehose port (#2942): stage 2's first consumer

- **signal-cli and the extraction agent** move into the firehose connector's boundary. Plaintext never reaches the worker.
- **Output** becomes intake items of the hub's chosen report type, sealed to `intake`. The connector can't read its own past output.
- **Deleted in the same change, with no fallback:**
  - `firehose_connections.encrypted_agent_nsec` and `FIREHOSE_AGENT_SEAL_KEY`;
  - the in-worker inference;
  - `firehose:read` and `firehose:manage`;
  - the firehose message-buffer and window-key tables.

  The per-window forward-secrecy buffers become the connector's own local, TTL-bound state.
- **Pilot data:** existing firehose report conversations stay readable as format-1 conversations and migrate with the conversation re-encryption job (#2964). Existing connections are not migrated. Each hub that uses the firehose re-enrolls it as a connector, which is an admin action shown in the release notes.

## 10. Contract surface and gates

**Contract PR (one, per #2977 "How this ships"):**
- the crate module (§8);
- `packages/protocol` schemas: manifest core and private, the enrollment request, the intake write, the `intake` purpose, and the connector auth union;
- the worker: `hub_connectors`, connector middleware and routes, the intake table and routes, the registry check, and quotas;
- **vectors:**
  - `manifestHash`;
  - enrollment AEAD;
  - intake `sig`;
  - `dedupTag`;
  - a chain with enroll → re-enroll → revoke and the expected item verdicts;
  - a server-substituted `intake` epoch key, which must be refused.

**Then adoption, one PR per client:** the enrollment approval screen, the inbox, confirm/merge/discard,
the revoked-connector flags, and the revoke dialog. Desktop goes first, then iOS and Android. None
is dropped. Each follows when its client's v2 sealed store is in place.

**Stage 1 gate (principals):**
- On real clients, a revoked connector's later items are refused, and nothing can be sealed to it, from each client's own chain.
- A server-substituted `intake` key is refused by the SDK.
- A user key on a connector route, and a connector key on a user route, both get 401.

**Stage 2 gate (inbound):**
- The firehose runs as a connector end to end.
- The worker has no route or code path that receives message plaintext from it, shown by the deletions in §9 and a grep gate.
- A reviewer confirms an item into a record on desktop and on one mobile client, and the record's evidence opens on both.
