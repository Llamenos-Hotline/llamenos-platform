# Encryption model v2: wire format (stage 0 + stage 1 formats)

**Date:** 2026-11-24 · **Base:** `origin/main` @ `fa575b14b` · **Epic:** #2974 (M2 critical path)
**Status:** DRAFT. Every choice marked **OPERATOR DECISION** needs sign-off before any code is written.

This document makes the wire decisions that stage 0 of #2974 ("one wire format") is waiting on.
#2961 says #2771's envelope encoding "is decided together with this header, not before", so this
spec decides both together. It also fixes the byte formats for the stage 1 hub authority chain
(#2963), so the one contract PR (#2974 "How this ships", step 1) can build the crate, the protocol
schemas, the worker and the cross-platform vectors from one document.

It covers:

1. one HPKE envelope encoding and label binding (#2771(b), #1649);
2. the v2 DEK header and the AAD rules (#2961 §Model 2);
3. `crypto_format` values and how M1 pilot rows migrate (#2964, #2947 comments);
4. one events format (#2768);
5. the hub authority chain link format (#2963, including the account-recovery addendum);
6. cross-platform test vectors.

**Not in scope.** This spec does not cover reader *semantics*: who is in which group, the rotation
schedule, availability UX, or organisations (#2294, stage 4). Those are settled in #2961 v2 and
#2963, and this spec only encodes them. Chunked file layout is #1145, and this spec fixes only the
blob's leading `crypto_format`. Index token layout beyond its key model (A5) is left to #2947. The
spec changes no code.

### Notation

```

u8(x), u16be(x), u32be(x), u64be(x)   fixed-width unsigned integers, big-endian
```

## 1. One HPKE envelope encoding (#2771(b), #1649)

### 1.1 Today, measured on the base

- **Two encodings of one envelope.**
  - `HpkeEnvelope {v: 3, labelId, enc, ct}` uses base64url (`hpke_envelope.rs:76`). It is stored
    whole for some values (PUK wraps in `puk.rs`, platform-role names).
  - `KeyEnvelope {enc, ct}` and `RecipientKeyEnvelope {pubkey, enc, ct}` use hex and carry no
    `labelId` (`encryption.rs:32,42`). Every note, message, record and hub-key wrap uses this form.
- **Opening the hex form rebuilds a v3 envelope** from the label the caller already expects
  (`encryption.rs:77-94` `hpke_unwrap_key`; the host shims listed in #2771). So the explicit
  `resolved_label != expected_label` check (`hpke_envelope.rs:159`) compares the expected label
  with itself, and can never fire on that path.
- **The real defence is HPKE `info`.** The label is bound as `info` on seal and on open
  (`hpke_envelope.rs:114,190`), so a wrong label fails the AEAD.
- **#1649 status.** The desktop half is fixed on this base. `wrap_hub_key_for_member` now returns
  the hex `KeyEnvelope` (`apps/desktop/src/crypto.rs:963`), `mobile_load_hub_key` refuses base64url
  (`ffi_v3.rs:2054`), and `hpkeEncSchema` enforces 64 lowercase hex characters for `enc`
  (`schemas/common.ts:7`). Two gaps are still open:
  - `ct` is still `z.string().min(1).max(512)` in `recipientEnvelopeSchema`, `keyEnvelopeSchema` and
    `fileKeyEnvelopeSchema`. Its comment still says "base64 overhead".
  - The crate reader is lenient. `decode_wire_bytes` (`encryption.rs:305`) accepts either hex or
    base64url, so an encoding drift is accepted quietly instead of being refused at the boundary.

### 1.2 D1: one envelope shape — OPERATOR DECISION

| Option | Shape | For | Against |
|---|---|---|---|
| **A** | `{enc, ct}` everywhere. No `v` and no `labelId`. The label is implied by the shape, and the crate supplies it | It is what every key wrap already stores. It deletes every host shim and the iOS magic `0`. The format version moves to `crypto_format` on the row (§3), where the server can see it and select on it. It removes most of the reason the numeric `labelId` exists | It drops the explicit early reject for readers of the full envelope (see Properties) |
| B | The full `HpkeEnvelope {v, labelId, enc, ct}` everywhere | Each envelope describes itself | It adds 2 fields to roughly 500 call sites' worth of rows. The `labelId` is redundant whenever the receiver knows what it is opening, which is always the case in v2, where the crate opens by shape. It also keeps the two-sources-of-truth hazard alive on the wire |
| C | A as raw binary (`enc ‖ ct`, 80 bytes) inside a binary header | Smallest | Every API is JSON, and it splits encodings again |

**Recommendation: A.**

- **The label is a parameter of the shape, never of the caller.** The crate exposes
  `seal_to(pubkey, Shape, aad_fields)` / `open_from(secret, Shape, aad_fields, wrap)`, following the
  `case_record.rs` pattern. `Shape` is a closed enum, and the crate maps each shape to its label,
  its `info` and its AAD builder. No host can name a label or an AAD (#2771(a)).
- **`LABEL_REGISTRY` keeps its role** as the closed set of allowed labels: seal still refuses an
  unregistered label. Its indices stay frozen by the append-only snapshot for as long as any
  numeric id survives. After the v1 code is deleted (§3.5), the only `labelId`s left are in format-1
  rows that no longer exist. The registry is then just the set, and its snapshot test keeps
  guarding against index reuse at no cost.
- **Everything stored whole as an `HpkeEnvelope` today moves to `{enc, ct}`** inside a format-2
  row: PUK wraps, `role-envelopes`, and platform-role names. Pre-production, so this is a rewrite,
  not a migration, except for any pilot rows (§3).

**Properties.** The label stays bound as HPKE `info`, unchanged. One thing is lost: the explicit
reject *before* HPKE runs, for a reader holding a full envelope. Nothing cryptographic is lost,
because the receiver supplies the label and a wrong one fails the AEAD with the same opaque
`DecryptionFailed`. #2771 asked that this be called out rather than assumed, and this paragraph
does that.

### 1.3 D2: one byte-string encoding on the JSON wire — OPERATOR DECISION

| Option | For | Against |
|---|---|---|
| **Lowercase hex** for every byte string in JSON | PROTOCOL.md §2.7 already says hex. `hpkeEncSchema` already enforces it. Every pubkey, hash and token field is already hex. A regex can enforce it in the schema. It was #1649's reading | Content blobs are 2× their byte size, against 1.33× for base64url |
| base64url (no padding) | Smaller blobs | Two of the three platforms converged on hex. It reopens #1649 and is harder to pin with a regex |
| Hex for keys and wraps, base64url for content blobs | Size where it matters | Two encodings again, which is exactly the class of bug #1649 is |

**Recommendation: lowercase hex everywhere in JSON. Large binaries (file chunks, recordings) are
raw request and response bodies, never JSON strings (#1145).** Summary tiers are small, and padding
(D6) dominates their size anyway.

**Enforcement, all in the contract PR:**

- `packages/protocol` adds `hexBytes(n)` and `hexBytesMin(n)` schema helpers. `enc` is
  `hexBytes(32)` (64 characters). A key-wrap `ct` is `hexBytes(48)` (96 characters: a 32-byte key
  plus the 16-byte tag). A content blob is `hexBytesMin(28)` (nonce 12 plus tag 16), even length.
- Uppercase is refused, not normalised. The pubkey and enc regexes are already lowercase-only.
- The crate's `decode_wire_bytes` stops accepting base64url. Anything that is not exactly `2N`
  lowercase hex characters is `InvalidFormat` at the boundary (the #1649 verification case 2).

## 2. The v2 DEK header (#2961 §Model 2)

### 2.1 Objects

| Object | Definition |
|---|---|
| **group** | `(hub, purpose)` per #2961, identified by `group_id` = 16 random bytes, `hex` on the wire (32 characters). It is declared by its first `group_epoch` link (§5.6). It is opaque: the server learns the group's *kind* from the chain, never the hub's vocabulary |
| **epoch** | `u32`, starting at 1, +1 for each `group_epoch` link of that group |
| **epoch keypair** | `sk` = 32 fresh random bytes, used as an X25519 static secret, and `pk = X25519(sk)`. **Never derived from a previous epoch** (#2961 A3). The `pk` is signed into the hub chain; the `sk` is granted per recipient (§2.8) |
| **DEK** | 32 random bytes, one per (document, tier) write (D5) |
| **header** | one HPKE wrap of a tier's DEK to one recipient: a group epoch `pk`, or a thread key (§2.7) |
| **document** | `(hub, type_ref, doc_id)`. `type_ref` is the opaque per-hub type id from #2961's generic store |
| **tier** | a closed enum owned by the crate (#2947): `summary = 1`, `fields = 2`, `pii = 3`, `hub = 4`, `thread_key = 5`, `message = 6`. `plaintext` has no ciphertext and no number. Adding a tier is a crate change, not a definition change |

**Identifier profile.** Every id that enters an AAD or a chain link (`hub_id`, `doc_id`, `type_ref`,
user and device pubkeys) must match `^[0-9a-z][0-9a-z-]{0,63}$` or be lowercase hex. The crate
refuses anything else instead of normalising it. `hubs.id` is `text` today, so the contract PR must
confirm that every existing hub id fits this profile.

### 2.2 Content ciphertext

```
padded   = padding::pad_to_bucket(plaintext)                    // D6: [u32le len][pt][random]
nonce    = random(12)
blob     = nonce ‖ AES-256-GCM(DEK, nonce, padded, aad = content_aad)   // ct ‖ tag(16)
wire     = hex(blob)
```

### 2.3 D3: how an AAD is encoded — OPERATOR DECISION

| Option | For | Against |
|---|---|---|
| A string joined with `:` (the v1 style, `"{label}:{recordId}:{field}"`) | Familiar, and readable in a debugger | Ambiguous whenever a component can contain `:`. It is spelled by hand at each site, which is the #1393/#2499 drift class |
| Canonical JSON | One canonical form shared with the chain | Needs a canonicaliser on the hot path of every seal and open, and invites hosts to build it themselves |
| **Length-prefixed binary tuple, fixed field order, built only in the crate** | Unambiguous by construction. No canonicalisation. Cheap. Every field has a fixed type | Not human-readable (the vectors show the bytes) |

**Recommendation: the length-prefixed tuple.** Every v2 AAD starts with `lp(utf8(label))`. Every
v1 AAD is a bare UTF-8 string starting `llamenos:`, so a v2 AAD begins with `0x00` (the high byte of
a short length) and can never equal a v1 AAD. That keeps a format-1 reader from ever opening
format-2 bytes, and the reverse (§3.4).

### 2.4 D4: what each AAD binds — OPERATOR DECISION

**Content AAD:** #2961's `(hub, type, doc, tier, schema version)`, plus the format.

```
content_aad =
    lp(utf8(L_V2_CONTENT))
  ‖ u16be(crypto_format)          // = 2; binds the format, so a relabelled row cannot be opened (§3.4)
  ‖ lp(utf8(hub_id))
  ‖ lp(utf8(type_ref))
  ‖ lp(utf8(doc_id))
  ‖ u8(tier)
  ‖ u32be(schema_version)          // the definition version the tier was written under
```

**Header AAD:** the content AAD, plus `(group, epoch)` from #2961, plus the writer's validated
chain head from #2963 §2. The head is what makes fork detection work on every document read.

```
header_aad =
    lp(utf8(L_V2_HEADER))
  ‖ lp(content_aad)                // the whole content AAD, length-prefixed
  ‖ u8(recipient_kind)             // 1 = group epoch, 2 = thread key (§2.7)
  ‖ recipient_id                   // 16 bytes: group_id, or thread_id = the conversation/call doc's id hash (§2.7)
  ‖ u32be(epoch)                   // group epoch, or thread-key generation
  ‖ u64be(head_seq) ‖ head_hash    // 32 raw bytes; the hub-chain head the writer validated
```

**Alternatives that were considered:**

- **Leaving the chain head out of the header AAD.** That is smaller, but #2963 §2 puts the head
  "into the header AAD" so a client reading another member's write can detect a fork. If it sits
  in a clear column without being bound, the server can rewrite it. **Keep it.**
- **Binding a write counter (a document version) against rollback.** The reader has no independent
  reference to compare a counter with, so it would detect nothing, and no issue in scope asks for
  it. **Leave it out**, and record rollback by the server as a stated non-goal (§8).

**Recommendation: as shown.** The crate exposes no way to build either AAD outside `seal_entity`
and `open_entity`.

### 2.5 D5: DEK lifetime — OPERATOR DECISION

- **Recommended: a fresh DEK each time a tier's content is written.** Its headers are written in
  the same request. A **header re-wrap** (revocation, A4; definition change; the #2947
  reconciliation) keeps the DEK and the content blob, and replaces only headers. This is what
  makes re-wrap "headers only".
- Alternative: one DEK for the document's whole lifetime. That saves wraps on edit, but a device
  that once read the document keeps reading every later edit across any number of re-wraps. **Not
  recommended.**

### 2.6 D6: padding — OPERATOR DECISION

Today record tiers are not padded, so a ciphertext's length leaks its plaintext length: a case's
status display, the length of a short note. The format can only change cheaply now.

- **Recommended: pad every tier with the crate's existing `padding` module** (powers of two,
  minimum 512 B, `[u32le length][plaintext][random]`). That is the same format the event relay
  already uses, so there is one implementation to audit.
- Alternatives:
  - no padding (status quo);
  - a smaller minimum bucket for tiers, which means a second padding variant;
  - Padmé, which leaks less on large plaintexts but is a new implementation.

### 2.7 Header wire shape

There is one header per (document, tier, recipient). The tier's readers are the list of groups its
definition declares (#2961 A1).

```json
{
  "tier": 1,
  "rk": 1,
  "rid": "<hex 16 B: group_id>",
  "epoch": 7,
  "head": { "seq": 412, "hash": "<hex 32 B>" },
  "enc": "<hex 32 B>",
  "ct":  "<hex 48 B>"
}
```

```
ct = HPKE.Seal(pk = recipient pk, info = utf8(L_V2_DEK_WRAP), aad = header_aad, pt = DEK)
```

**Server-written headers.** For inbound messages, voicemail, transcription and call metadata, the
server seals through `sealFor(hub, purposes[], userGroups[])` (#2961) to the chain-signed epoch
`pk`. It binds the head it stores. Clients apply the same fork check to it as to any other writer's
head.

**Storage.** `sealed_document_headers(hub_id, doc_id, tier, rk, rid, epoch, head_seq, head_hash,
enc, ct)`, with primary key `(doc_id, tier, rk, rid)`. The document row carries `crypto_format`, and
no header outlives its document (shredding deletes the headers, per #2961).

- A **re-wrap** is a compare-and-set update of one row, `WHERE epoch = <old>`, so it is idempotent
  and resumable.
- **The server write guard** reads only clear columns: for each declared sealed tier, a header
  exists for every declared group **at that group's current epoch per the chain**. This is the exact
  admin guard from the #2961 reader-set comment: one key id, known from the chain.

**Thread keys** (#2961 comments, "thread key"; not hub-chain groups) use the same header with
`rk = 2`:

- `rid` = the first 16 bytes of `H(lp(utf8(L_V2_THREAD_ID)) ‖ lp(utf8(hub_id)) ‖ lp(utf8(doc_id)))`
  for the conversation or call document.
- `epoch` = the thread-key generation (1 at open, +1 on each claim or transfer).
- The thread key's X25519 secret is itself a `thread_key` tier of the conversation document, with
  headers to `responders` and `admins` (or to the claimant's user group and `admins` after a
  claim).
- Each generation is published as a signed record:
  ```
  { "thread": "<doc_id>", "gen": n, "pk": "<hex 32 B>", "signer": "<device ed25519 hex>", "sig": "<hex 64 B>" }
  sig = Ed25519(device, utf8(L_V2_THREAD_KEY_SIG) ‖ 0x00 ‖ lp(utf8(hub_id)) ‖ lp(utf8(doc_id)) ‖ u32be(gen) ‖ pk)
  ```
  This gives integrity between clients without a chain link, as #2961 states. A generation-1 key
  made by the server at conversation open carries no device signature and is marked
  `"signer": null`. The server already sees the plaintext of inbound messages, so this gives it
  nothing new.
- Message tiers (`tier = 6`) are sealed to the thread key's current generation.

**What changes for messages.** Messages get the bound content AAD for the first time. They had no
AAD because client-sealed and server-sealed messages shared a conversation with no format marker
(`envelope_aad.rs` header). In v2, `crypto_format` is that marker, and both writers build the same
AAD through the crate (the server through `ffi_server`).

### 2.8 Grants: an epoch secret wrapped to a recipient

Grants are rows, not links (#2963 §7):

```
group_grants(hub_id, group_id, epoch, rkind, rkey, owner_user, enc, ct,
             granter_device, granter_head_seq, granter_head_hash, sig)
  rkind: 1 = device X25519 key, 2 = the owner's PUK dh key (user groups only, #2961 Model 1), 3 = hub escrow key

grant_aad = lp(utf8(L_V2_GROUP_GRANT)) ‖ lp(utf8(hub_id)) ‖ group_id(16) ‖ u32be(epoch)
          ‖ u8(rkind) ‖ rkey(32) ‖ lp(utf8(owner_user))
          ‖ u32be(puk_generation)                    // 0 unless rkind = 2
                                                     // owner_user is the empty string for rkind = 3 (escrow)
ct  = HPKE.Seal(pk = rkey, info = utf8(L_V2_GROUP_GRANT), aad = grant_aad, pt = epoch_sk)
sig = Ed25519(granter_device, utf8(L_V2_GRANT_SIG) ‖ 0x00 ‖ grant_aad ‖ enc ‖ ct
              ‖ u64be(granter_head_seq) ‖ granter_head_hash)
```

**Opening a grant.** The recipient, and every client auditing per A2, must check four things:

1. `rkey` is active in `owner_user`'s verified user sigchain (rkind 1). The device arrived by a path
   that is not a recovery link still lacking its approvals (#2963 addendum).
2. `owner_user`'s chain-derived state places them in the group.
3. `granter_device` is authorised per its user sigchain, and its user may manage this group per the
   hub chain at `granter_head` (§5.5).
4. **`X25519(epoch_sk)` equals the `pk` in the chain's `group_epoch` link for `(group, epoch)`.**
   Without check 4, a server could wrap a key of its own choosing to a device's public key, which
   anyone can do, and the device would adopt it. That is the analogue of the hub-key rotation
   `check` (PROTOCOL.md §2.7).

A failure in check 1, 2, 3 or 4 is a visible alert, never a silent skip.

### 2.9 D7: index keys (#2961 A5) — OPERATOR DECISION

Index keys are symmetric, so they have no public half to sign into the chain. **The attack:** a
server wraps a key it knows to a member's device. Anyone can seal to a public key. The member then
computes tokens the server can brute-force for low-entropy fields (statuses, dates, badge numbers).

- **Recommended:**
  - The `group_epoch` link that introduces or carries an index version includes
    `index: { "version": v, "commit": hex(HMAC-SHA256(index_key, lp(utf8(L_V2_INDEX_COMMIT)) ‖ lp(utf8(hub_id)) ‖ group_id ‖ u32be(v))) }`.
  - The key itself is wrapped once per epoch to that epoch's `pk`:
    `index_key_wraps(hub_id, group_id, version, epoch, enc, ct)`, with `info = L_V2_INDEX_WRAP`, AAD
    the same tuple. Any member opens it with the epoch secret it already holds.
  - Clients verify the commitment before computing a single token.
  - This costs one wrap per epoch instead of one per device, and needs no new link type.
- Alternative: wrap index keys per device, like grants, with no commitment. **Not recommended**,
  because the substitution attack above stays open.

Which fields are indexed, and how tokens are built, stay with #2947 and the definition format. The
`document_index_tokens` table is #2961's.

## 3. `crypto_format` and the M1 pilot migration (#2964)

### 3.1 D8: values — OPERATOR DECISION

| Value | Meaning |
|---|---|
| `0` | Invalid. Never written; a row carrying it is refused |
| `1` | **M1 pilot**: per-device envelope lists, label-only content AAD (`envelope_aad.rs`), no AAD on stored messages, hub-key-sealed small fields |
| `2` | **v2**: this document (group and thread-key headers, bound AADs, padding) |
| any other | Refused by every client and by the server. Never guessed, never trial-decrypted (#2964) |

**Where it lives:**

- A `crypto_format smallint NOT NULL CHECK (crypto_format IN (1, 2))` column on every sealed row.
  #2964 adds it in M1 with value `1`. The `2` arm of the CHECK lands in the contract PR.
- The first two bytes, `u16be`, of every sealed blob (the rest of a v2 blob's layout is #1145).
- The content AAD (§2.4).

No column has a database default after #2964 backfills. A writer that omits the value is refused.

### 3.2 Order of operations, per hub

1. **Migration genesis** (#2963 §4). A current admin signs the migration genesis listing the
   members the server reports, and confirms the list on screen. Without a chain there are no groups,
   so a hub without a chain cannot hold format-2 rows.
2. **Groups.** The admin client creates `admins`, `members` and the purpose groups the definitions
   declare, and each member's per-hub user group (that link is signed by the user's own device, per
   #2963 §5, on that user's next sign-in). Escrow, if set, is in each `group_epoch` (§5.6).
3. **Re-encryption job** (§3.3). It runs on an admin client.
4. **Per-type cutover** (§3.5).

### 3.3 The re-encryption job

#2947: binding the new content AAD is a full re-encryption, not a header re-wrap.

The job is the same client-side job runner as the A4 re-wrap, the A5 re-index and the #2947
reconciliation, built once in the crate. It selects rows by `crypto_format = 1` and, for each row:

1. Opens each tier through the **format-1 reader**, with the admin's device key or escrow.
2. Seals each tier fresh as format 2 (§2), with the same `doc_id` and `type_ref`, and headers for
   the tier's declared groups.
3. Calls `POST /api/hubs/:hubId/documents/:id/migrate { expectedFormat: 1, expectedVersion, tiers, headers }`.
   The server, in one transaction, compare-and-sets on `(id, crypto_format = 1, version)`, replaces
   the tier blobs, inserts the headers, **deletes every format-1 envelope**, and sets
   `crypto_format = 2`. A lost race is a 409 and a re-read.

Properties:

- **Resumable and idempotent:** a row already at format 2 is skipped.
- **A row no current admin or escrow can open is reported** with its id, type and reason, never
  skipped silently and never deleted (#2947, the #2174/#2190 class).
- **Progress** is reported the way #2961 A4's "re-wrap pending" is.
- **Hub-key-sealed small fields** (tags, teams, role names, `shifts.encrypted_name`) are rows of the
  same job. They move from `encryptForHub` to the DEK/header shape under `members` (#2961, "the hub
  key today, and the move"). The hub key and `resealAll` are deleted when the last such row of the
  last hub is at format 2.

### 3.4 Downgrade and confusion

- **A format-2 row relabelled to `1` by the server** fails the format-1 reader. Its content AAD is
  the bare label, and the v2 blob was sealed under a binary AAD that starts with `0x00`.
- **A format-1 row relabelled to `2`** fails because there is no header, and the AAD differs.
- **A reader never tries one format after another fails.** It reads the column and opens with
  exactly one reader.

### 3.5 Cutover and deleting v1

- Per #2974 stage 3, "the legacy envelope path is no longer written": **for a type ported to v2 on
  all three clients, the server refuses format-1 writes** for that type. #1618 stays until messages,
  notes, call records and files are ported (#2961 Sequencing).
- **The format-1 readers are deleted** once the migration job reports zero format-1 rows on every
  hub of the deployment. There is no legacy fallback after that point (root `CLAUDE.md`). Their
  fixtures (§6) are deleted in the same PR.

## 4. One events format (#2768)

### 4.1 Today

- **The server-event format is the one in use.** The relay publishes every frame with it
  (`ws-events.ts` `encryptEventContent`), and `server-event-vectors.json` pins it:
  ```
  epoch     = floor(unix_seconds / 86400)
  key       = HKDF-SHA256(ikm = SERVER_SECRET, salt = utf8(L_SERVER_EVENT_ENCRYPTION_KEY),
                          info = utf8(L_HUB_EVENT_EPOCH ":" epoch), 32)
  payload   = hex(nonce(12) ‖ AES-256-GCM(key, nonce, pad_to_bucket(utf8(json)),
                                          aad = utf8(L_HUB_EVENT_EPOCH ":" epoch)))
  ```
- **The hub-key event format has no producer on this base.** `encryptHubEvent` is referenced only
  by its own module and its unit test. It still has readers: `encryption::decrypt_hub_event`,
  `mobile_decrypt_hub_event` and its `_with_attribution` and `_trial` variants, desktop
  `decrypt_hub_event`, `platform.ts` `decryptHubEvent`, iOS and Android `decryptHubEvent`.
  PROTOCOL.md §2.8 "Hub-Wide Broadcasts" also disagrees with the crate: it says
  `HKDF(hub_key, info = "llamenos:hub-event")`, while `decrypt_hub_event` uses the hub key directly.
  Unexecuted code drifts like this.
- **The server derives the event key two different ways:** `ws-events.ts` `getOrDeriveEpochKey`
  and `hub-event-crypto.ts` `deriveServerEventKey`, which also has an unused per-hub salt branch.
- **Some readers take the key from the host,** `decrypt_server_event_hex`, even though the same key
  is already held in Rust by `mobile_set_server_event_keys`.

### 4.2 D9 — OPERATOR DECISION

| Option | What changes |
|---|---|
| **A: keep the server-event bytes; delete the hub-key event format** | One crate `events` module: `seal_server_event(server_secret, epoch, json)` (server, via `ffi_server`) and `open_server_event(epoch, payload)` against keys held in crate state on each client. The info, AAD, padding and key derivation are composed once, in Rust. Deleted: every hub-key event reader listed above, `mobile_decrypt_server_event` (the epoch-less AAD under the server key), `decrypt_server_event_hex`, both TypeScript derivations, and `encryptHubEvent`/`decryptHubEvent`. PROTOCOL.md §2.8 "Hub-Wide Broadcasts" is removed. No wire change |
| B: keep both formats, each moved into the crate | Keeps a format nobody writes, so it can drift again |
| C: move the hub-key event format onto the `members` group | Pointless. #2961 says events are "transient or server-known by design" and stay off groups |

**Recommendation: A.** The `server-event-vectors.json` fixture stays exactly as it is and becomes
the events module's conformance test. The crate PR must re-confirm that the hub-key format has no
producer before deleting it (#2768).

**Found while writing this, not proposed here.** The server-event key is account-wide: every hub of
an instance shares it. Its AAD binds the epoch but not the hub or the event kind, so a frame could
be replayed into another hub's stream. Changing either of those is a wire change, and none of the
in-scope issues asks for it. It needs its own issue (§8).

## 5. Hub authority chain link format (#2963)

### 5.1 Link envelope

```json
{
  "hub": "<hub_id>",
  "seq": 1,
  "prevHash": null,
  "signerUser": "<user ed25519 pubkey hex>",
  "signerDevice": "<device ed25519 pubkey hex>",
  "signerUserHead": { "seq": 3, "hash": "<hex 32 B>" },
  "body": { "type": "genesis", "...": "..." },
  "entryHash": "<hex 32 B>",
  "sig": "<hex 64 B>"
}
```

- `seq` starts at 1, and the server enforces `UNIQUE(hub, seq)`. An append is a compare-and-set
  against the head: the loser gets a 409, re-reads, **re-evaluates its authority against the new
  head**, re-signs and retries (#2963 §1).
- `prevHash` is `null` only at `seq = 1`.
- **`timestamp` is deliberately absent from the signed form.** The user sigchain signs a timestamp
  that nothing verifies. Ordering is `seq`; the time a link was appended is a server column.
- `signerUserHead` is the signer's user-sigchain head under which `signerDevice` is active (§5.4).

**Storage.** `hub_chain_links(hub_id, seq, prev_hash, entry_hash, link_json, appended_at)`.
`users.hub_roles` becomes a cache of the chain-derived state that clients never trust (#2963).

### 5.2 D10: canonical serialisation — OPERATOR DECISION

| Option | For | Against |
|---|---|---|
| **Sorted compact JSON** (the user sigchain's rule, `sigchain.rs:72-152`), **under a restricted profile** | Reuses a canonicaliser that already has cross-language vectors. Readable. Servers store and serve JSON | JSON canonicalisation has corners: escaping, numbers, Swift's default `\/` escaping |
| Deterministic CBOR (RFC 8949 §4.2.1) | Well-specified | A new dependency and a new audit surface on four platforms; not readable |
| A bespoke length-prefixed binary format | No ambiguity | A new format to version and document, and a second canonical form beside the user sigchain |

**Recommendation: sorted compact JSON under this profile**, and **computed only in the crate**
(clients through UniFFI or Tauri, the server through `ffi_server`). No host ever hashes a link
itself, which removes the cross-language canonicalisation risk:

- Object keys are ASCII camelCase, sorted at every depth.
- Values are only: integers `0 ≤ n ≤ 2^53 − 1`; strings matching `^[0-9a-z:_.-]*$` (ids, hex,
  enum words); arrays; objects; and `null` only for `prevHash` at `seq = 1`.
- **There is no free text in a link.** Role vocabulary stays sealed (#2963), so links name opaque
  ids and hashes only. The escaping corners cannot arise.
- **Set-valued arrays** (members, holders, bundles) are sorted ascending and unique. The verifier
  rejects an unsorted or duplicated array instead of sorting it.
- `entryHash = H(utf8(canonical(link without entryHash and sig)))`.
- The verifier **re-canonicalises from the parsed value and compares**. The server may therefore
  store the link as `jsonb`: integers and the string profile survive jsonb's normalisation.

### 5.3 D11: signature — OPERATOR DECISION

```
sig = Ed25519(signerDevice, utf8(L_HUB_CHAIN_SIG) ‖ 0x00 ‖ entryHash(32 raw bytes))
```

The user sigchain signs the raw `entryHash` with no label (`sigchain.rs:180-182`). A hub link
without a label would be one canonicalisation coincidence away from a valid user link, and the
reverse. The label makes the two unconfusable, whatever happens to either canonical form.

- **Recommended:** label the hub chain as shown, and leave the user sigchain's signature unchanged.
  Changing it is not in scope, and the hub chain's label is enough to separate the two in both
  directions.
- Alternative: also relabel the user sigchain in the same contract PR. That is cleaner, but it
  breaks every existing user-chain vector and touches #1972's in-flight work.

### 5.4 Who may sign: validation rules

A link at `seq = n` is valid iff all of these hold:

1. The hash chain links up (`prevHash` equals the `entryHash` at `n − 1`), and `entryHash` and
   `sig` verify.
2. `signerDevice` is active in `signerUser`'s **verified** user sigchain at `signerUserHead`.
3. `signerUser`'s permissions in the **chain-derived state at `n − 1`** allow this body type, per
   #2963 §5:
   - role management for `role_grant`, `role_revoke`, role-group `group_epoch`, `connector_*`,
     `policy`, `checkpoint` and `recovery_group`;
   - the escrow-management permission for `escrow_set`;
   - **the subject user themselves** for a user-group `group_epoch`.
4. The body is valid for its type (§5.6).

Authority races resolve by construction: an admin revoked at `n` cannot land a link built on
`n − 1` (#2963 §1).

**D13: stale signer heads — OPERATOR DECISION.** A device removed from its user chain at user seq
`s` could still sign a hub link that references an older user head `< s`, where it was active.

- **Recommended rule:**
  - **Validity is deterministic.** Every verifier must reach the same verdict on the same chain, so
    validity never depends on what one verifier happens to know locally. The chain-derived state
    keeps, per user, the highest `signerUserHead.seq` any accepted link has referenced. A new link
    by that user must reference a head at or above it, and `signerDevice` must be active at that
    head. Once any of a user's hub links references a head after a removal, the removed device
    can never sign for that user in that hub again.
  - **Advisory alert, not a validity rule:** a verifier whose copy of the signer's user chain shows
    `signerDevice` removed at a user seq above `signerUserHead.seq` raises the stale-signer alert.
    This is the same detection channel as #2963 §2.
  - **Residual:** until one of the user's hub links references a post-removal head, the removed
    device can still sign links that verify. State it, as #2963 §2 does for detection versus
    prevention. The user's own clients close it at their next hub action.
- Alternative: every `device_remove` in a user chain triggers a hub-chain `user_head` link in each
  of the user's hubs. That closes the window, but it is a link type #2963 does not list, and it
  costs O(hubs) links per device removal.

### 5.5 D12: bundle permissions — OPERATOR DECISION

#2963 says: "Links name opaque permission-bundle ids … the permission set a bundle grants is
committed by hash in the link."

```
perms_hash = H(lp(utf8(L_HUB_BUNDLE_PERMS)) ‖ lp(utf8(p_1)) ‖ … ‖ lp(utf8(p_k)))   // p_i: system permission ids, sorted, unique
```

| Option | Shape | Cost of editing a bundle's permissions |
|---|---|---|
| **A** | `policy { kind: "bundle", bundle, permsHash }` commits the hash once. `role_grant { user, bundle }` names the bundle only | One link |
| B | `role_grant { user, bundle, permsHash }`, as #2963 is literally worded | One re-grant link per holder |

**Recommendation: A.** Both commit by hash in a link, so the intent of #2963 is kept.

**Verification needs the plaintext permission set.** A verifier opens the sealed bundle definition
(a sealed document under `members`) and checks its hash. Headless connectors cannot read that
document.

- **Open question for the operator:** either connectors join a `definitions` read group, or the
  permission list travels in clear in the `bundle` policy link. System permission ids such as
  `settings:manage` are not hub vocabulary; role *names* are, and those stay sealed either way.
- **Recommendation: carry the permission ids in clear**, because a connector has to evaluate who
  may sign the `admins` epoch it seals to (#2963 acceptance, "connector SDK test").

### 5.6 Link bodies

All ids follow §2.1. Every set is sorted and unique (§5.2).

| `type` | Body fields | Signer (§5.4) |
|---|---|---|
| `genesis` | `founder` (user), `migration` (bool as `0`/`1`), `members: [{user, bundles: [bundle]}]` (for migration: the list the admin confirmed on screen, #2963 §4; for a new hub: the founder alone) | the founder's device. Its validity is the trust anchor (#2963 §3), not chain state |
| `role_grant` | `user`, `bundle` | role management |
| `role_revoke` | `user`, `bundle` | role management |
| `group_epoch` | `group` (16 B hex), `kind` (`purpose` \| `user` \| `connector`), `subject` (purpose: a closed system purpose word such as `admin`, `members` or `call-history`, from `READER_PURPOSE_PERMISSIONS`; user: the user pubkey; connector: the connector id), `epoch`, `pk` (hex 32 B), `escrow` (the escrow pubkey in force, or absent; #2963 §5 "escrow joins every group"), `reason` (`create` \| `removal` \| `schedule` \| `device`), optional `index: {version, commit}` (D7) | role management; for `kind = user`, the subject user's own device |
| `connector_enroll` | `connector`, `signingPk`, `encryptionPk`, `manifestHash` (#2939 owns the manifest) | role management |
| `connector_revoke` | `connector` | role management |
| `escrow_set` | `pk` (hex 32 B), or absent to remove | escrow-management permission |
| `policy` | `kind` plus fields per kind: `bundle` (D12); `rotation` with `group` and `periodDays`; `recovery_quorum` (optional, off by default; #2963 §6) | role management |
| `recovery_group` | `groupPk` (hex 32 B), `threshold` (2–5, matching `hub_recovery_groups.threshold`), `holders: [user]`, `commitments` (H of the share commitments), `delayHours`, `emergencyFloorHours` | role management |
| `checkpoint` | `state` = `H(canonical(chain-derived state at n − 1))` | role management |

**Group membership is derived, never listed.**

- A `purpose` group's members are the users whose chain-derived permissions include
  `READER_PURPOSE_PERMISSIONS[subject]`.
- A `user` group's members are that user's active devices and PUK.
- A `connector` group's member is the connector.

Adding a member is a grant (§2.8), never a link. That keeps chain growth to "role changes plus
epochs" (#2963 §7).

**Epochs.** The first `group_epoch` for a `group` must have `epoch = 1` and `reason = create`. Each
later one is `+1`. `subject` and `kind` never change for a group.

### 5.7 Head references (fork consistency, #2963 §2)

Every signed client write names the hub head it validated:

- chain links name it through `prevHash`;
- grants through `granter_head`;
- headers through the header AAD.

A reader whose chain has a different hash at that `seq` raises the fork alert and stops sealing in
that hub. A reader whose chain is shorter fetches forward first.

**Anchors** come from a trusted device, never from the server (#2963 §3). Their wire shape is
`{hub, seq, hash}`, carried in the provisioning payload (#1972), the invite, and the connector
enrollment handshake. Those payloads' own formats belong to their issues.

### 5.8 D14: recovery link (#2963 addendum) — OPERATOR DECISION

**Approval.** Each contributing holder signs one approval:

```json
{
  "type": "recovery_approval",
  "hub": "<hub_id>",
  "hubHead": { "seq": 0, "hash": "<hex>" },
  "subjectUser": "<user pubkey>",
  "newSigningPk": "<hex 32 B>",
  "newEncryptionPk": "<hex 32 B>",
  "session": "<recovery session id>",
  "holderUser": "<user pubkey>",
  "holderDevice": "<device ed25519 pubkey>",
  "sig": "<hex 64 B>"
}
```

```
sig = Ed25519(holderDevice, utf8(L_RECOVERY_APPROVAL) ‖ 0x00 ‖ H(utf8(canonical(approval without sig))))
```

It uses the same canonical profile as §5.2. It replaces today's unchecked `contributorSignature`,
which names neither the user nor the new keys.

**User-sigchain link.** It is signed by the new device:

```json
{
  "type": "recovery_device_add",
  "devicePubkey": "<newSigningPk>",
  "encryptionPubkey": "<newEncryptionPk>",
  "hub": "<hub_id>",
  "hubHead": { "...": "..." },
  "session": "...",
  "approvals": ["≥ K approvals, sorted by holderUser"],
  "emergency": "<absent, or one approval-shaped object signed by an admins-group member>"
}
```

**`verify_sigchain` rule.** The link is valid iff:

1. it carries at least `threshold` approvals from **distinct** `holderUser`s in the
   `recovery_group` holder set **as of `hubHead`**;
2. each approval's `holderDevice` is active in that holder's user chain;
3. every approval's `subjectUser`, `new*Pk`, `session` and `hubHead` match the link's.

The new device then joins the active set. `emergency` only shortens the delay
(`emergencyFloorHours`), which the server enforces. It never substitutes for the threshold.

**Naming.** The addendum writes `recovery-device-add`. **Recommended:** `recovery_device_add`, to
match the existing underscore link types (`device_add`, `puk_epoch`). Also note that today's user
genesis payload is `type: "user_init"` while the `linkType` column enum says `genesis`
(`schemas/sigchain.ts:31,50`). That mismatch is kept as it is and is out of scope.

**Until this lands,** clients refuse to seal PUK or user-group epochs to a device that arrived by a
recovery link (#2963 addendum).

## 8. Non-goals, and findings for separate issues

**Non-goals of the v2 format:**

- **Rollback.** A server serving an older ciphertext of the same document and tier is not
  detected. Neither is a header older than the current epoch that still opens.
- **Sender authentication of record content.** Any member of a tier's groups can write a
  well-formed tier. Integrity is AEAD-to-group, as it is today with per-device envelopes. Thread
  keys are the one signed object (§2.7).
- **Forward secrecy for stored records.** No scheme provides it (#2961 A3).

**Findings while writing this, which need their own issues if the operator wants them:**

- The server-event key is shared by every hub of an instance, and its AAD binds neither the hub
  nor the event kind (§4.2).
- PROTOCOL.md §2.8 "Hub-Wide Broadcasts" describes an HKDF step that the crate's
  `decrypt_hub_event` does not perform. Recommendation D9 deletes both.
- `recipientEnvelopeSchema.ct` and its siblings are unconstrained, and their comment says base64.
  D2 fixes this.
- `decode_wire_bytes` accepts base64url as well as hex. D2 fixes this.
- The user-sigchain genesis is `user_init` in the payload but `genesis` in the `linkType` enum
  (§5.8).
